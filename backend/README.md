# Backend — NHL Stats Dashboard API

FastAPI service plus a set of standalone ingestion scripts that pull data
from the NHL's public API into Postgres, and one script that runs its own
Monte Carlo playoff-odds simulation. See the [top-level README](../README.md)
for the full picture — this doc is the "how do I run this" reference.

The API process only ever *reads* from Postgres. All writes happen in the
ingestion scripts below, run on a schedule or manually — the live API
never calls the NHL directly, so it stays fast and isn't affected by a
slow or unreachable upstream.

## Database credentials: two separate roles

This "API only reads" split is enforced at the database level, not just
by convention:

- **`DATABASE_URL`** — owner-level credential. Used only by the
  ingestion scripts (`ingest_*.py`, `backfill_season_history.py`,
  `simulate_playoff_odds.py`), which need `INSERT`/`UPDATE`/DDL access.
- **`API_DATABASE_URL`** — a least-privilege, read-only role
  (`nhl_api_readonly` in this project's Neon instance). Used only by
  `api.py`.

`api.py` fails loudly at startup (`RuntimeError`, not a silent fallback
to `DATABASE_URL`) if `API_DATABASE_URL` isn't set — see `get_connection()`.
That's deliberate: if the API's credential were ever leaked, the blast
radius is "read the data" instead of "read, write, and drop tables."

## Setup

1. Create a Postgres database (Neon, Supabase, Railway, or local).
2. Apply the schema:
   ```
   psql "$DATABASE_URL" -f schema.sql
   ```
3. Create a read-only role for the API and grant it `SELECT` on every
   table in `schema.sql` (`GRANT SELECT ON ALL TABLES IN SCHEMA public
   TO nhl_api_readonly;` or equivalent) — this is what `API_DATABASE_URL`
   should point at.
4. Install dependencies:
   ```
   pip install -r requirements.txt
   ```
5. Copy `.env.example` to `.env` and fill in both database URLs — the
   owner-level one for `DATABASE_URL`, the read-only role's for
   `API_DATABASE_URL`:
   ```
   cp .env.example .env
   ```
6. Run whichever ingestion scripts you need (see below), then start the API:
   ```
   uvicorn api:app --reload
   ```
7. Visit `http://127.0.0.1:8000/docs` for interactive API docs
   (auto-generated by FastAPI from the code).

## Running the tests

```
pip install -r requirements-dev.txt
pytest
```

No database or `.env` is required — the test suite never opens a real
Postgres connection (see "Testing strategy" below), so it runs the same
way locally and in CI with zero setup. `pytest.ini` points pytest at
`tests/`, so plain `pytest` from the `backend/` directory is all that's
needed. Useful variations:

```
pytest -v                              # verbose, one line per test
pytest tests/test_api_roster.py        # just one file
pytest -k playoff_teams                # tests matching a keyword
```

### Test suite layout

```
tests/
  conftest.py                    # fake DB layer + shared fixtures (see below)
  test_simulate_playoff_odds.py  # pure-function tests: win_probability, determine_playoff_teams
  test_ingest_advanced_stats.py  # pure-function tests: time_to_seconds
  test_api_misc.py               # GET /, GET /teams, GET /playoff-odds
  test_api_roster.py             # GET /teams/{team}/roster
  test_api_players.py            # GET /players/leaders, GET /players/{id}
  test_api_standings.py          # GET /standings/latest, GET /standings/{team}, GET /standings/{team}/seasons
```

### Testing strategy: mocked DB layer, not a real database

Every DB-touching function in `api.py` goes through the same narrow seam:
`get_connection()` → `conn.cursor()` → `cur.execute()` /
`.fetchone()`/`.fetchall()`. The test suite patches `get_connection()` to
return a fake connection whose cursor is backed by canned, per-query
responses (see `DBRouter`/`FakeCursor`/`FakeConnection` in
`tests/conftest.py`) instead of standing up a real Postgres instance.

Why mocking instead of a test database:

- **No infrastructure required.** Tests run with no Postgres install, no
  Neon branch, no `DATABASE_URL` pointed at anything real — confirmed by
  running the suite with `.env` removed entirely. That means CI needs
  zero secrets to run this suite, and a fresh clone works immediately.
- **Zero risk to production data.** There is no path in the test suite
  that can open a real connection, so there's no possibility of a test
  accidentally reading or writing the live Neon database — not "we're
  careful," but structurally impossible.
- **Fast and deterministic.** All 61 tests run in well under a second, no
  network calls, no flakiness from shared state or connection limits.
- **The queries themselves were already verified against real data.**
  The response-model work in this project involved fetching real rows
  from every endpoint and confirming they validate against the Pydantic
  models. This test suite's job is to lock in the *contract* (status
  codes, response shape, the 404-vs-empty-list behavior, request
  validation) rather than re-prove SQL correctness — mocking is the right
  tool for that job.

The tradeoff: these tests can't catch a typo in raw SQL (a real Postgres
would reject bad syntax; the mock happily returns whatever you configure
it to). That's an accepted gap for this suite's scope — a `LEFT JOIN
LATERAL` or `NUMERIC` column mistake would still surface immediately the
first time someone runs the app against a real database, just not from
`pytest`.

## Ingestion scripts

All read the owner-level `DATABASE_URL` from `.env` (not `API_DATABASE_URL`
— see "Database credentials" above) and are safe to re-run — everything
upserts, nothing duplicates.

| Script | What it pulls | How often |
|---|---|---|
| `ingest_standings.py` | Current standings, all 32 teams → one snapshot row per team per day | Daily |
| `ingest_player_stats.py` | Current roster + season-to-date stats, all 32 teams | Weekly in-season (season totals don't need daily polling) |
| `ingest_advanced_stats.py` | 5-on-5 Corsi/Fenwick, computed from play-by-play + shift-chart data across every completed game | Weekly in-season |
| `simulate_playoff_odds.py` | Monte Carlo playoff-odds simulation (`--as-of` for backtesting a past date) | Daily |
| `backfill_season_history.py --years N` | Final standings for the last N completed seasons | One-time, or to extend the range |

Scheduled via Windows Task Scheduler (`ingest_standings.py` at 6:00am,
`simulate_playoff_odds.py` at 6:10am). The others are run manually — see
the top-level README for why.

## API endpoints

| Endpoint | Returns |
|---|---|
| `GET /health` | Actually exercises the database (`SELECT 1` via the read-only role) — 200 if reachable, 503 if not. Exempt from rate limiting, for Azure Container Apps' probes / an uptime monitor. `GET /` is a static "process is up" payload and doesn't check the database at all. |
| `GET /teams` | All 32 teams |
| `GET /standings/latest` | Most recent day's standings, all teams |
| `GET /standings/{team}` | Full daily-snapshot history for one team (`?start=&end=` optional) |
| `GET /standings/{team}/seasons` | Final standings for that team's last 5 completed seasons |
| `GET /playoff-odds` | Latest Monte Carlo playoff-odds simulation, all teams |
| `GET /teams/{team}/roster` | Current roster + season stats for one team |
| `GET /players/leaders` | Every rostered player + season stats (league leaderboard) |
| `GET /players/{id}` | Bio + season-by-season stats + advanced stats for one player |

## Schema

- `teams` — static team metadata
- `standings_snapshots` — one row per team per day, current season
- `season_final_standings` — one row per team per completed season (last 5 years)
- `players` — current roster snapshot, all 32 teams
- `player_season_stats` — one row per player per season, refreshed each ingestion run
- `player_advanced_stats` — computed Corsi/Fenwick, one row per player per season
- `playoff_odds` — Monte Carlo simulation results, one row per team per as-of-date

Full column definitions and comments are in `schema.sql`.

## Error tracking

Optional, via [Sentry](https://sentry.io). Set `SENTRY_DSN` in `.env` (a
free Sentry project's DSN) and `api.py` reports unhandled errors there;
leave it unset and the app just runs without error reporting — this is
an operational nice-to-have, not a required credential like
`API_DATABASE_URL`, so a missing DSN never blocks startup.

Only 5xx responses are reported (Sentry's Starlette/FastAPI integration
default) — expected 4xx responses (a bogus team abbreviation's 404, a
too-long path param's 422, a rate-limited request's 429) are normal
application flow, not errors, and don't get reported. Set
`SENTRY_ENVIRONMENT=production` in the Container App's real environment
variables so production issues aren't mixed in with local-dev noise
(defaults to `"development"` if unset).

## Deployment

Dockerized, deployed to Azure Container Apps. `../azure-piplines.yml`
builds the image on every push to `main` that touches `backend/`, pushes
it to Azure Container Registry, and updates the running Container App.

## Notes

- `season_id` format is `20252026` for the 2025-26 season.
- `streak_code` is `'W'`, `'L'`, or `'OT'`; pair with `streak_count`.
- `standings_snapshots` is unique per `(snapshot_date, team_abbrev)`, so
  re-running the ingestion the same day just no-ops on conflict.
